# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository.

## What this is

Cuotia collects recurring community fees (vigilancia now, administración later) for urbanizaciones and conjuntos in Colombia. Residents pay by Bre-B; **pagoradar** (a separate, already deployed service, `ingenieroedward/pagoradar`, read-only reference, never modify it from here) reads the bank notice and sends Cuotia a signed `payment.received` webhook. Cuotia owns the ledger: houses, dues, payments, aliases. It is **multi-tenant**: each conjunto sees only its own data. Pilot: Jardines de Ibiza (~45 houses, $30.000/month, one person holds the bank account).

## Commands

```bash
npm test                         # node:test, test/**/*.test.js
MASTER_KEY=$(openssl rand -hex 32) npm start
npm run admin -- crear-conjunto --slug ibiza --nombre "Jardines de Ibiza" --correo tesorera@ejemplo.com --llave @llave --titular "Titular"
npm run admin -- agregar-casa --conjunto ibiza --codigo 14 --residente "Sandra Duque"   # prints the resident's personal link
npm run admin -- generar-cuotas --conjunto ibiza --periodo 2026-11
```

No build step, no linter, **no runtime dependencies** (keep it that way: `node:sqlite`, `node:crypto`, `node:http`). Requires Node ≥ 22.5.

## Architecture

```
pagoradar ──signed webhook──▶ POST /webhooks/pagoradar/<tenantId> ─▶ verify with THAT tenant's secret ─▶ ingestEvent ─▶ store.forTenant(tenantId)
```

- **`src/app.js`**: plain `(req, res)` router. Per-conjunto webhook `/webhooks/pagoradar/<tenantId>` (HMAC check over the exact body *before* parsing, with the secret of the tenant in the URL), login/logout, panel, resident link `/r/<token>`, one static file.
- **`src/store.js`**: single SQLite DB, migrations `V1`… by `PRAGMA user_version` (never edit an earlier one). **Tenant isolation rule: all data of a conjunto is reached through `store.forTenant(id)`**, which closes over the tenant id. Never add a query on tenant data outside it. The only global lookups are `tenants`, `users`, `sessions` and `residentByToken` (the unguessable token is the credential). Every method that takes a house/payment id re-checks it belongs to the tenant. `test/isolation.test.js` guards this: extend it whenever you add a repo method.
- **`src/pagoradar.js`**: `ingestEvent` maps a verified event to ledger changes. **The conjunto is the one in the webhook URL** (whose secret signed the event); an optional `data.account.tenantRef` must equal it or the event is ignored (`tenant_mismatch`). It auto-settles only when the payer matches **one** house (remembered alias, else unique name match) **and** that house has an open due for exactly the amount; everything else goes to the "por asignar" queue. Never guess. Idempotent by pagoradar payment id, stored as `<tenantId>:<id>` so two conjuntos' pagoradars can reuse ids.
- **pagoradar config is per conjunto and lives in the DB, never in env.** `tenants.pagoradar_secret` is AES-GCM encrypted with `MASTER_KEY` (V3); the tenant DTO exposes only `pagoradarConfigured`/`pagoradarLastAt`, never the secret. Set from the panel (`/panel/ajustes`) or `npm run admin -- configurar-pagoradar`. No secret yet → the URL answers 503 so pagoradar retries. Any correctly signed event (even `payment.test`) updates `pagoradar_last_at`, which Ajustes shows as "Conectado". Do not reintroduce a global pagoradar secret.
- **Matching model:** dues are charged at the exact base amount (no unique-amount trick). `payments.assign(..., {rememberAlias})` teaches Cuotia the payer's name for next time.
- **`src/security.js`**: scrypt passwords, session/resident tokens (only SHA-256 hashes stored), pagoradar signature check (same algorithm as pagoradar's SDK: `Pagoradar-Signature: t=…,v1=HMAC(secret,"t.body")`, 5-minute tolerance), attempt limiter, AES-256-GCM `encryptSecret/decryptSecret` with `MASTER_KEY`, TOTP (RFC 6238, no library), per-session CSRF token.
- **Passkeys** (V19 `passkeys`, `webauthn_challenges`, `src/webauthn.js`, `forTenant().passkeys`, Ajustes → "Passkeys", login button "Entrar con passkey"). No library: CBOR reader, authData parser, COSE→SPKI, ES256 and RS256, attestation "none". Discoverable credentials with **user verification required**, so a passkey sign-in counts as password *and* second step and creates a `full` session directly (audited "Inició sesión con passkey"); password + TOTP stay as the fallback and for recovery. Challenges are single-use rows (3 min) bound to the purpose (and to the user when registering); `signCount` may not go backwards; `userHandle` must be that user's id; rpId = hostname of `PUBLIC_URL`, origin = its origin (so a wrong `PUBLIC_URL` breaks passkeys). Max 5 per user; failures share the login limiter and a good sign-in clears it. Global lookups allowed: `passkeys.byCredentialId`/`touch`, `webauthnChallenges`. Not for the operator panel. Verified with a fake authenticator (`test/fake-authenticator.js`), not yet on a real iPhone/Android (an installed iOS PWA may behave differently from Safari).
- **Access recovery, self-service** (V21 `recovery_codes`, `access_resets`; `newRecoveryCodes`/`normalizeRecoveryCode`/`recoveryHash` in `security.js`; `forTenant().recovery`, `team.resetAccess`, global `recoveryCodes.consume` and `accessResets.byToken/use`; routes `/olvide`, `/2fa/respaldo`, `/restablecer/<token>`, `/panel/respaldo/generar`, `/panel/celular/cambiar`, `/panel/equipo/<id>/acceso`; card "Si pierdes el acceso" in Ajustes). There is **no email/SMS in Cuotia on purpose** (no dependencies, nothing to send with), so recovery rests on three things: (1) **ten backup codes** (`XXXXX-XXXXX`, no 0/O/1/I/L, ~49 bits, shown once after re-typing the password, only an HMAC with `MASTER_KEY` stored, single use, regenerating replaces all). A code opens the 2nd step when the phone is lost (`/2fa/respaldo`, pending sessions only, shares the 5-try `codeLimiter`) or lets the person set a new password at `/olvide` (email + code + new password; same generic error for an unknown email and a wrong code, always hashes the new password so timing doesn't tell, limited per IP and per email, signs out every session, audited). (2) **"Cambiar mi celular"** in Ajustes (password re-typed): clears TOTP and every session, the next sign-in enrolls a new phone. (3) **A colleague's one-use link** (Equipo → Restablecer acceso, 24 h, only the hash stored, shown once, same conjunto only, never for yourself): the person chooses a new password; **old password, TOTP, passkeys, backup codes and sessions are all discarded**. If someone is the only member and has lost everything, the operator's CLI (`restablecer-2fa` / `restablecer-clave`) remains the last resort. Audit lines never carry a code or a link. The operator panel has its own login and is not covered by this.
- **Login is two steps and mandatory.** Password → a short session with `stage` `pending` (has TOTP) or `setup` (must enroll); only `/2fa` accepts it. A valid code → `sessions.promote` issues a *new* `full` session (token changes at privilege change). TOTP secrets are stored encrypted; `users.claimTotpStep` makes each code single-use. Lose `MASTER_KEY` and nobody can sign in: back it up. Every panel route requires `stage === "full"`.
- **First run: `/setup?token=…`.** With no conjunto in the DB, `server.js` prints a private one-use link (token = `SETUP_TOKEN` or random per boot). The form creates the first conjunto, its "Vigilancia" concept and the treasurer with a password they choose. `setupOpen` = no tenants AND `safeEqual(token)`; otherwise it answers the normal 404 so it never reveals whether setup exists. Re-checked synchronously after the async password hash so two simultaneous submits create one conjunto (tested). Wrong tokens are rate limited. There is deliberately **no open sign-up**: more conjuntos are created by the operator from `/operador` (see below).
- **`src/qr.js`: QR generator with no dependencies** (byte mode, level L, versions 1-9 = up to 230 bytes; `qrSvg` returns an inline SVG with colors as attributes because the CSP forbids inline styles). It draws the 2-step enrollment QR (an `otpauth://` link, ~100 bytes = version 5). It was verified against an independent decoder (jsQR, in a scratch dir, not a dependency) for every length 1-230 and against the page rendered in Chromium in light and dark mode. The repo's own tests (`test/qr.test.js`) read a symbol back (format info, mask, zigzag, Reed-Solomon, text) so a regression in placement or masking fails CI. Don't add a QR library; if the link ever exceeds 230 bytes, extend the tables to versions 10+ (16-bit character count).
- **Operations (`src/schedule.js`, `src/backup.js`, `scripts/admin.js`).** `generateAllDues` runs on boot and hourly from `server.js` (idempotent), so nobody has to press "Generar cuotas": without it a payment arriving before that finds no open due and waits in "por asignar". Adding or reactivating a house also generates the current period right away. `respaldar` uses `VACUUM INTO` (consistent while the app runs), never overwrites an existing file, names files to the second (`cuotia-AAAAMMDD-HHMMSS.db`, UTC) and prunes only files matching that name. `restablecer-2fa` / `restablecer-clave` are the recovery path for a lost authenticator or password (they also sign the user out everywhere). Changing the password from Ajustes needs the current one, is rate limited like login, and signs out every other session. HSTS is sent only when `PUBLIC_URL` is https. Bulk house import (`parseHouseLines` in `text.js`, `/panel/casas/importar`) shows each new personal link once, like a single new house.
- **Manual payments work without pagoradar** (`payments.recordManual`, `/panel/pagos/nuevo`). One payment can settle several dues of one house (they share `payment_id`), for exactly their sum: there are no partial payments. All or nothing inside a transaction; every due must be this house's, this tenant's and pending. `external_id` is `manual_<id>` (old cash ones are `cash_<id>`) and `payments.manual` is derived from that prefix, **not** from `method`, because pagoradar also reports `method: "transfer"`. The date is a Colombia-time day: today = now, a past day = noon that day (so it lands in the right month), future or before 2024 is refused. `revert` deletes a manual payment (it exists only here) and puts all its dues back to pending. `paymentMedium(p)` is the single label used by lists, receipts and the CSV. The resident pay screen says "avísale al tesorero" instead of "cuando el banco lo confirme" when the conjunto has no pagoradar secret.
- **Installable app (PWA).** `public/manifest.webmanifest` (treasurer, `start_url` `/panel`) and a **per-resident manifest** generated at `/r/<token>/manifest.webmanifest` (`start_url` and `scope` = that personal link, name "Cuotia · Casa 14"), so each resident installs an app that opens on their own due; `layout()` takes a `manifest` option and the three resident pages pass theirs. Icons are `public/icons/` (rounded `icon.svg`/PNGs for "any", full-bleed `maskable` and `apple-touch-icon` because the OS applies its own mask), generated from the two SVGs with Chromium (not a dependency); `favicon.ico` is a PNG-in-ICO of the 32 and 48 px. **`public/sw.js` must be served from `/` with `Cache-Control: no-cache`** (a cached worker can't be fixed) and **must never cache a page or a non-GET**: pages carry payments, names and personal tokens. It only network-first caches `/static/*` and answers navigations offline with `/offline`. `test/server.test.js` runs `sw.js` in a `node:vm` sandbox to prove those rules, and Chromium (`Page.getInstallabilityErrors`) reported no errors for both manifests. Not tested on a physical iPhone/Android. Bump `CACHE` in `sw.js` if the cached asset list changes.
- **How payments are confirmed** (V9 `tenants.pay_mode` `auto|manual|NULL`; Ajustes → "¿Cómo confirmas los pagos?"). The DTO exposes the effective `payMode` (NULL = `auto` if a pagoradar secret is saved, else `manual`). It only changes what the resident reads on the pay screen ("cuando el banco lo confirme" vs "cuando el tesorero registre tu pago" and a primary upload-proof button); the webhook works regardless of the mode.
- **Phone notifications / Web Push** (V10 `settings`, `push_subscriptions`, `forTenant().push`, `src/webpush.js`, `notify()` in `app.js`). No library: VAPID (ES256 JWT) + `aes128gcm` payload encryption with `node:crypto`, checked against the RFC 8291 test vector. The VAPID key pair is created on first use (private half encrypted with `MASTER_KEY`; if it can't be decrypted new keys are made and subscriptions dropped). Each person subscribes a device from Ajustes → "Avisos en el celular" (`public/app.js` + `push`/`notificationclick` in `sw.js`); iPhone needs the installed app (iOS ≥ 16.4). Notified: a resident uploads a proof, a pagoradar payment arrives (assigned or not; only the amount, never a payer name, goes on a lock screen). `notify` never throws or delays the request; a 404/410 removes the subscription. **The endpoint comes from the browser, so `validEndpoint` allows only Google/Mozilla/Apple/Microsoft push hosts over https (no SSRF).** `createApp` accepts a `pushSend` stub for tests.
- **Cuentas claras** (V11 `expenses`, `tenants.opening_cents` / `show_accounts`, `forTenant().expenses` and `.books(period)`, `/panel/cuentas`). The treasurer records expenses (fixed `EXPENSE_CATEGORIES`, a 5 MB photo/PDF receipt verified by magic bytes like proofs, multipart with `_csrf` as a field) and **voids** a mistake instead of deleting it (it stays listed as "anulado" and stops counting). `books` = money in (payments `assigned`, by `paid_at` in the Colombia month) − money out (expenses not voided); **cash balance = opening balance + all income up to the end of the month − all expenses up to it**. Residents see it only when the treasurer ticks "Mostrar las cuentas a los residentes" (off by default; otherwise `/r/<token>/cuentas` answers 404): totals, categories and the expenses with receipts, never voided ones. Receipts are served with `nosniff`, `default-src 'none'; sandbox`, `no-store` (PDF downloads). The month text for the neighbours' WhatsApp group is built by `accountsText`; there is no public link (only personal ones).
- **Public transparency page** (V20 `tenants.public_token_hash` / `public_token_enc`, `tenants.byPublicToken` / `setPublicToken` / `clearPublicToken`, `/t/<token>` in `app.js`, `transparenciaPage`, card "Página pública de transparencia" in Cuentas claras). Off by default; the treasurer activates it, can **change the link** (the old one dies) or **turn it off**; all three are audited without ever writing the link. The token is random (24 bytes); only its SHA-256 is used to look it up (global lookup, allowed like `residentByToken`) and a copy is encrypted with `MASTER_KEY` so the panel can show the link again. Public means anyone with the link, no sign-in: so it shows **only** the month's totals (collected, spent, cash balance, houses al día as counts) and the non-voided expenses' category, date, text and amount. **Never a resident, a house code, a payer name or a receipt file** (those stay behind personal links; a test greps the page for them), `noindex` (header and meta), `no-store`, no manifest. Unknown tokens are rate limited and answer the plain 404. Expense descriptions are free text typed by the treasurer, and the panel warns not to put personal data in them. Independent from "Mostrar las cuentas a los residentes".
- **Personal link in reminders** (V22 `houses.access_enc`, `houses.setSealedLink` / `sealedLinks`, `hasLink` on the house DTO, `keepLink` in `app.js`, `{tu_enlace}` in `recordatorio_casa`). Lookup is still by hash, but the app now also keeps the token **encrypted with `MASTER_KEY`** (never in the clear, never in an audit line) so the treasurer's per-house WhatsApp reminder can include it. It is saved whenever a link is created or regenerated (panel, import, `agregar-casa` with `MASTER_KEY`), cleared when a house's personal data is erased, and only active houses return one. `panel()` decrypts them once per request into `house.link`, which `personalReminder` turns into `Tu enlace personal (guárdalo, es solo tuyo): <url>`; no stored link → the variable is empty and the line vanishes (no blank hole). **Houses created before V22 have no stored link** (the old token cannot be recovered): their Casa page says so and offers "Generar enlace personal nuevo" (which kills the old link). A conjunto that edited `recordatorio_casa` keeps its own text until it adds `{tu_enlace}`. Treat the DB + `MASTER_KEY` together as able to open every resident's page.
- **Notifications to residents** (V12 `house_push_subscriptions`, `reminders_sent`, `forTenant().housePush` / `.reminders`, `src/notifier.js`, `sendReminders` in `schedule.js`). A resident turns them on from their home (`data-resident` card; same client code as the treasurer's, posting to `/r/<token>/avisos/suscribir|baja`, credential = the personal link, same-origin, rate limited; only active houses of that conjunto can subscribe). The push payload never carries the personal link, so the phone itself remembers it (`caches` entry `resident-link`, written by the page) and the service worker resolves the payload URL `@resident[/pagar]` into it on click. Triggers: **"Pago confirmado"** whenever a payment gets assigned to a house (manual, `assign`, or pagoradar auto-match; `notifyConfirmed`) and the hourly **reminders** "Hoy vence tu cuota" (day = `due_day`) / "Tu cuota venció" (day after), between 8 and 20 h Colombia, only to subscribed houses that still owe this month, only in conjuntos that set a last day to pay, once per house/month/kind (`reminders.claim`, so restarts never repeat). `createNotifier` is shared by the app and `server.js` (same VAPID keys); `createApp` accepts `pushSend` or a ready `notifier` for tests.
- **Estado de cuenta and paz y salvo** (V13 `certificates`, `serveDocument` in `app.js`, `estadoPage`/`pazYSalvoPage`/`verificarPage`). Printable pages (the browser's print dialog = PDF, `noprint` hides the buttons) at `/r/<token>/estado|paz-y-salvo` for the resident and `/panel/casas/<id>/estado|paz-y-salvo` for the treasurer (ownership re-checked; a house dada de baja answers 404). The estado lists every due with its state (`late` from `groupDebts`, never recomputed) and totals. **A paz y salvo is issued only when the house has no overdue dues** (this month's still-pending due is fine; it says "no registra cuotas vencidas"); otherwise the page says what is overdue and issues nothing. Each certificate gets a random code (no 0/O/1/I/L), stored once per house/kind/day (`certificates.issue`), checked by anyone at `/verificar?codigo=` through the global `certificates.byCode`, which returns only conjunto name, house number, kind and day, **never a resident's name**; lookups are rate limited. Note `.doc-table` overrides the generic mobile "cards" table rule.
- **Audit log** (V14 `audit_log`, `forTenant().audit`, `auditFor` / `audit()` in `app.js`, `src/audit.js` for the filter labels, `/panel/bitacora` linked from Ajustes). Append-only (no update/delete method exists) and per conjunto. Every **successful** state change in the panel writes one fixed Spanish sentence with the person's name as it was then (the user may be removed later): payments recorded/assigned/undone, proofs rejected, houses created/edited/dada de baja/de alta/link regenerated/imported, payment names, dues generated, expenses recorded/voided, settings, team invitations/removals, password change and each sign-in. **Failed attempts leave nothing, and a summary must never contain a secret, a password or a file**: write the sentence from ids and amounts, never from form values like `secret` or `nueva`. When you add a panel action, add its `audit(...)` line after it succeeds and extend the "bitácora" server test.
- **What a conjunto charges** (V15 `concepts.kind` `monthly|once`, `/panel/conceptos` "Qué cobras", under Más). **Monthly** concepts (Vigilancia, Administración…, `concepts.list()`) get a due per active house every month (boot, hourly, and right away when added or resumed); `setAmount` only affects dues made afterwards (existing ones keep what they were charged); the last active monthly one can't be paused. **Special charges** (`concepts.charge`: cuota extraordinaria to all houses, multa to one) create a `once` concept plus one due per chosen active house for a month, all or nothing, name unique; they are never regenerated. **Matching a payment to dues is `dues.matchFor(houseId, amount)`, used by both `ingestEvent` and `assign`, deterministic and never a guess:** (1) one due with exactly that amount (oldest, then by concept name); (2) else all unpaid dues of one month when several add up exactly; (3) else all the house's unpaid dues when they add up (the resident's "Total a pagar"); otherwise it waits in "por asignar". A payment can therefore settle several dues (shared `payment_id`; `revert` puts them all back). The sidebar shows `Cuota mensual <sum>` when there are several monthly concepts. Copy must stay neutral ("tu cuota", never hard-coded "vigilancia").
- **Data protection (Ley 1581)** — `/privacidad` (`privacidadPage`, public, same text for every conjunto: the conjunto is the *responsable*, Cuotia the *encargado*; env `PRIVACY_CONTACT` is the optional contact, otherwise it says to ask the treasurer). `layout()` adds a footer link to it on every non-panel page (`legal: false` for the panel shell, printable documents and the receipt). It is a **base text the owner must have a lawyer review**; if the app starts keeping a new kind of personal data or sharing it with a new provider, update the sections "Qué datos se tratan" and "Con quién se comparten". Right to erasure: `houses.anonymize(id)` (button on the page of a house **dada de baja**, `/panel/casas/<id>/anonimizar`, audited) renames it "Residente anterior", clears phone, payment names, proofs and push subscriptions and sets the payer name of its payments to "Pagador anónimo"; dues and amounts stay for the accounting. Irreversible, refused for an active house.
- **Operator panel** (V16 `operators`, `operator_sessions`, `src/operator.js`, views `operador*` in `views.js`, mounted at `/operador` from `app.js`). The platform owner (not a treasurer: belongs to no conjunto) creates operators **only from the terminal** (`npm run admin -- crear-operador --correo …` prints a temporary password once; `restablecer-operador` for a lost password/phone). Own table, own sessions and own cookie `cuotia_op` scoped to `Path=/operador`, so neither login can reach the other panel; same security as a treasurer (password + mandatory TOTP, same-origin, CSRF, rate limits). **Everything under `/operador` answers 404 until an operator exists.** It can: create a conjunto (name, monthly fee → the "Vigilancia" concept, optional key/holder, treasurer name and email → a one-use **invitation link** so the treasurer chooses their own password; the operator never sees a password), invite another person into an existing conjunto, change their own password. **It only ever sees counts** (houses, team, pending invitations, pagoradar status, last sign-in), built through each conjunto's own `forTenant` methods: never residents, payments or accounts; keep it that way. It writes "Se creó el conjunto" / "Invitó a …" (as "Equipo de Cuotia") in the conjunto's audit log. There is no way to delete a conjunto from the UI on purpose.
- **Start from scratch** (`/panel/reiniciar`, `forTenant().reset({keepHouses})` + `resetPreview()`, Ajustes → "Empezar de cero"). Erases **one conjunto's** operating data for good: dues, payments, proofs, expenses, special charges, certificates and reminders sent (and, with `keepHouses: false`, also houses, payment names and house phone notifications). Always kept: settings, monthly concepts, team and their phones, **the audit log** (which records "Empezó de cero…"). After it the current month's dues are generated again for the houses that remain. Guards, in this order: password re-entered (rate limited with the login limiter), the word `BORRAR` typed, and **a backup of the whole database first** (`config.backupDir`, default `<db folder>/backups`, env `BACKUP_DIR`; a copy made in the same second takes the next second's name; if no copy can be saved nothing is erased). Do not add a way to run it without those three.
- **Off-server backups** (`src/s3.js`, `src/offsite.js`, `offsiteDue` in `schedule.js`, scheduling in `server.js`, config `BACKUP1_*…BACKUP3_*` + `BACKUP_KEEP`, operator panel "Respaldos", CLI `respaldar-externo` / `probar-respaldo` / `descifrar-respaldo`). No library: AWS Signature V4 + put/list/delete over `fetch`, path-style, for any S3-compatible service (Cloudflare R2, Backblaze B2). The nightly run (2–6 a.m. Colombia once the last good copy is >20 h old, any hour after 36 h; first run 2 min after boot) does `VACUUM INTO` → **AES-256-GCM encryption streamed with a key derived (HKDF) from `MASTER_KEY`** (`MAGIC + iv + ciphertext + tag`) → upload to every destination (one failing never stops the others) → keeps only the newest `BACKUP_KEEP` files named like ours in each → deletes the temporary files → stores the result in `settings` (`offsite_last`, `offsite_last_ok`). **The cloud must only ever receive ciphertext** (a restore needs the same `MASTER_KEY`, so it must be backed up separately) and the operator panel shows destination names and results, never keys or endpoints. Incomplete `BACKUPn_*` groups are reported as warnings, never half-used, and never crash the app. `descifrar-respaldo` is the restore path (stop the app, replace the DB file). The signer is checked against Amazon's official canonical-request hashes, but only a real bucket proves the keys: use "Probar conexión".
- **Payment methods** (V17 `pay_methods`, `forTenant().payMethods`, `PAY_KINDS`/`payMethodTitle`/`payMethodAccount`/`paySummary` in `text.js`, Ajustes → "Otros medios de pago"). The **Bre-B key stays in the tenant** (`pay_key`/`pay_holder`, "Cuenta para cobrar"); besides it a conjunto lists up to 6 more (Nequi, Daviplata: 10-digit mobile starting with 3; Bancolombia: account number + ahorros/corriente; Otro: a name + number), each with optional holder and a short note. Validated and de-duplicated in the store. The resident's pay screen shows one card per method with a copy button (the raw number is copied, the phone is shown spaced), and **every WhatsApp reminder carries all of them through `paySummary(tenant)`**: panel views get them as `tenant.payMethods` (spread in `base`; the resident pay route does the same), so don't read `tenant.payKey` directly for "how to pay". pagoradar only reads the Bre-B account's bank, so payments through the other methods are registered by the treasurer or confirmed from the resident's proof. Audit lines name the method, never the number.
- **Editable WhatsApp messages** (V18 `message_templates`, `src/messages.js`, `forTenant().templates`, `/panel/mensajes` under Más). Three messages — `recordatorio_casa`, `recordatorio_general`, `enlace_casa` — each with an original text in `MESSAGES` and `{variables}` (`nombre`, `casa`, `conjunto`, `tesorero`, `meses`, `valor`, `detalle`, `plazo`, `como_pagar`, `casas`, `mes`, `valor_cuota`, `enlace`). A conjunto's edit is a row only when it differs (resetting deletes it). Saving is validated (15–1200 chars, only known variables, `enlace_casa` must keep `{enlace}`) and an invalid text is re-rendered on the same page with what was typed, never put in the URL. Views build them with `message(tenant, key, vars)`; the panel's `tenant` carries `templates`, `sender` (the signed-in person's name) and `monthlyCents`. **`renderTemplate` (server) and `renderMessage` (public/app.js, the live preview) must stay identical**: a test runs both on the same cases. **No emojis anywhere in what is sent**: some phones and WhatsApp's share page show them as "?"/"�"; `validateTemplate` refuses them and `message()` strips any saved before the rule (`hasEmoji`/`stripEmoji`). `{casas}` is one house per line. The per-house reminder carries the personal link through `{tu_enlace}` (see **Personal link in reminders**); the group reminder never can.
- **Debts are monthly and tracked across months** (`src/debts.js`). `groupDebts(pending, houses, period)` turns `dues.listPending()` into one entry per owing house, ordered the way a treasurer chases: houses with **overdue** dues (a month before the current one) first, then the oldest debt, then the biggest, codes sorted numerically. The current month is "pendiente", only previous months are "atrasada"; at the turn of the month yesterday's pending becomes overdue by itself. `panel()` in `app.js` computes the groups once per request and passes `debts`/`owing` to every page: the sidebar badge on **Por cobrar**, `/panel/cobros` (filters `f=atrasadas|mes`, search `q`), the dashboard's arrears card and "Para cobrar primero", the status pill and button on **Casas**, and the payment form picker. The dashboard takes `?mes=YYYY-MM` (only months that have dues; anything else falls back to the current month, and generating dues is offered only for the current one). Row buttons open `/panel/pagos/nuevo?casa=<id>&cuota=<dueId>` (that due ticked; `todas=1` ticks all, none = the oldest); a successful manual payment redirects to `/panel/cobros?m=manual`. Per-house WhatsApp reminders use `personalReminder`; without a phone the link is `wa.me/?text=` so WhatsApp asks who to send it to (the reminder carries the house's personal link when Cuotia has it, see **Personal link in reminders**). **Any list of houses that owe must come from `groupDebts`, never recomputed in a view.** Links with several query parameters must write `&amp;` in literal template text (interpolated values are escaped, literals are not).
- **Payment window per conjunto** (V6, `tenants.open_day` / `due_day`, 1-28, NULL = not set; Ajustes → "Fechas de pago"). Informational for the resident ("Paga del 1 al 10 de noviembre", `paymentWindow`) and it drives lateness: `groupDebts(..., {dueDay, day})` marks a due `late` when its month is before the current one **or** it is this month's and today (Colombia) is after `dueDay`; that day itself is still on time. Views read `group.lateMonths` / `due.late`, never compare periods themselves. Payments are accepted and matched on any day: the dates never block anything.
- **Proofs of payment** (V7 `proofs`, `forTenant().proofs`, `src/upload.js`). A resident uploads a photo/PDF (≤ 5 MB) at `/r/<token>/comprobante` (multipart parsed by hand; the type comes from the **magic bytes**, never from the browser, SVG/HTML are refused; max 3 pending per house; rate limited; same-origin). Bytes live in SQLite (backups include them) and only come back through `proofs.file(id)` for the treasurer, at `/panel/comprobantes/<id>/archivo` with `nosniff`, `default-src 'none'; sandbox`, `no-store` and a PDF forced to download. They appear in "Comprobantes por revisar" on the Resumen (and in the sidebar badge); **Registrar pago** with `comprobante=<id>` passes `proofId` to `recordManual`, which marks it `accepted` inside the same transaction; `revert` puts it back to `pending`; rejecting keeps the file. The upload page deliberately has no auto-refresh (it would clear the chosen file).
- **Team** (V8 `invitations`, `forTenant().team`, global `invitations.byToken/accept`). Ajustes → Equipo: any signed-in member invites by email; the link `/invitacion/<token>` (7 days, one use, only its hash stored, shown once) lets that person choose a name and password in the **inviting** conjunto, then they sign in and enroll their own 2-step code like anyone. Everyone has the same power (role stays `tesorero`); you can't remove yourself or the last person; removing deletes their sessions. Emails are globally unique, so an email of another conjunto can't be invited. Rate limited like setup.
- **Search is instant and works without JavaScript.** Lists carry `data-search`, inputs `data-live-filter` (and the empty-message id in `data-live-empty`); `public/app.js` filters as you type and hides the search button, Enter opens the only match's `[data-pick]` link. A `<select>` with many options gets a hidden `data-select-filter` input that the script reveals and that rebuilds the options. **`fold`/`matches` in `public/app.js` and `foldText`/`matchesSearch` in `src/text.js` must stay identical** (accent-less, case-less, every word in any order): the no-JS server search and the browser must answer the same; a test runs both on the same table. Use the `[hidden]` attribute (global `display:none !important`), not inline styles.
- **Months that were never generated.** Dues exist only for generated months (boot and hourly generate the current one). `dues.generateForHouse(house, period)` and `/panel/casas/<id>/mes` (the `+ Octubre` buttons in the payment form) add one month to one active house and return to the form with it ticked; `POST /panel/cuotas/generar` with `mes=` adds a month for every active house. `validPastPeriod` in `app.js`: a real month, not the future, at most 24 back. Both are idempotent (`INSERT OR IGNORE`), so the only way to double-charge is not available.
- **Every panel POST** checks same Origin **and** the session's `_csrf` form field (`csrfToken(sessionToken)`, HMAC of the HttpOnly cookie value). Flash messages come from a fixed list keyed by `?m=`; never reflect query text. **`Referrer-Policy` must stay `same-origin`**: with `no-referrer` browsers post forms with `Origin: null` and the Origin check refuses every login (found by a real-browser run; `fetch` tests can't see it).
- **`src/views.js` + `src/http.js`**: server-rendered HTML. The `html` tagged template escapes every interpolation unless it is `html`/`raw()` output; use it for all markup. CSP is `default-src 'self'` with no inline styles or scripts: use classes in `public/app.css`, never `style=""`.
- **Design:** the approved mockup canvas is https://claude.ai/artifact/57BSgLaPW6LwbXJpm8bk8L; the layout must keep matching it. Tokens and layout in `public/app.css`: palette **"Arena"** (minimalist, chosen by the owner after "Menta clara", which they stopped liking) = dark brown ink `#3b3028` (buttons, sidebar, tab bar, receipt page), sand accent `#ece3d6`, a **light sand hero card** `#f1ebe1` (`--hero-bg`, text `--hero-fg`; the hero's buttons are ink), ground `#faf8f5`, links `#8a4b1f`. The status colors (ok green, warn amber, info blue, bad red) stay semantic in both looks. Mobile first, **light by default**. A dark look exists but is **opt-in per device** (Ajustes → "Apariencia": Claro / Oscuro / Automático, saved in `localStorage` `cuotia-theme`; `public/theme.js` is loaded synchronously in `<head>` and sets `data-theme` on `<html>` before paint, `Automático` follows the OS). The CSS never uses `prefers-color-scheme` (a test guards it) so a user whose OS is dark still sees the approved design unless they choose otherwise. Dark = `:root[data-theme="dark"]` token overrides only; use tokens (`--chrome` sidebar/operator bar, `--on-accent`, `--hero-num`, `--bar-track`), never new hard-coded colors. QR, printable documents, receipt card and the WhatsApp preview stay white/green on purpose. App icons, favicon, manifests and `theme-color` use the same green/mint (icons regenerated from the SVGs with Chromium (brown/sand now); `favicon.ico` is rebuilt from the 32 and 48 px PNGs). The earlier mockup canvas (ink + lime, dark hero) is **outdated** in colors only. **Shell** (`panelLayout` in `views.js`): dark sidebar from 900px (every section), bottom tab bar below it with **five tabs only** (`TABS`: Resumen, Por cobrar, Casas, Pagos and **Más**, which opens `/panel/mas` with Cuentas claras, Ajustes and Bitácora; `MORE_KEYS` keeps Más highlighted inside them; six tabs did not fit an iPhone 12 mini, so a new section goes under Más, not in the bar); every treasurer page goes through it and gets `{tenant,user,csrf,badge,houseCount,cuota}` from `base` in `app.js`. **Resident pages** have no shell: home (`/r/<token>`), how to pay (`/r/<token>/pagar`, refreshes itself every 20 s and redirects home once nothing is pending) and receipt (`/r/<token>/recibo/<dueId>`, only for a paid due of that house; "Descargar PDF" is the browser's print with a print stylesheet). **Font:** Plus Jakarta Sans variable, self-hosted in `public/fonts/` (SIL OFL, licence file alongside); only the files listed in `STATIC` in `app.js` are served. **Script:** `public/app.js` only adds copy/print buttons (`data-copy`, `data-print`); the CSP allows scripts from this origin only, so no inline scripts and no `style=""`.

## Conventions

- User-facing strings (UI, errors, logs, docs) are **Spanish (Colombian)**; code identifiers and comments are English.
- Money is integer cents (`amountCents`); show with `peso()`. Periods are `"YYYY-MM"` in Colombia time (`currentPeriod()`).
- Tests: `node:test` + in-memory store, **made-up data only**. `test/fixtures.js` has `twoConjuntos()` and `paymentEvent()`.
- Deployment: Docker Compose on Dokploy. Data volume pinned to `cuotia-data`; don't rename it.

## Houses, history and undo

- A house is never deleted: `houses.setActive(false)` keeps all history but closes its personal link, skips it in `dues.generate` and in matching (`aliases.houseFor` and `matchHouse` only see active houses), and its **unpaid** dues stop counting in `summary`/`listByPeriod` (its **paid** ones keep counting).
- `payments.list({period,status,houseId,q,limit,offset})` is the history (newest first). `period` is a Colombia-time month (`periodRange`, UTC-5). The search escapes `LIKE` wildcards and skips the payer-name clause when the needle normalizes to nothing. The CSV (`/panel/pagos.csv`) is `;`-separated with a UTF-8 BOM (what Spanish Excel opens correctly) and every cell goes through `csvCell`, which neutralizes a leading `= + - @` so a payer's name can't run as a spreadsheet formula. Tests read the BOM from raw bytes because `fetch().text()` strips it.
- `payments.revert` undoes an assignment: the due returns to pending; a bank payment goes back to "por asignar" and the alias learned for that house is deleted; a cash payment (which exists only here) is deleted. The UI hides it inside `<details>` so a stray tap does nothing and no script is needed.
- Any new route that takes a house, alias or payment id must go through `forTenant` methods that re-check ownership, and needs a case in the "un tesorero no puede ver ni tocar…" server test.
