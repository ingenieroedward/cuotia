# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository.

## What this is

Cuotia collects recurring community fees (vigilancia now, administración later) for urbanizaciones and conjuntos in Colombia. Residents pay by Bre-B; **pagoradar** (a separate, already deployed service, `ingenieroedward/pagoradar`, read-only reference, never modify it from here) reads the bank notice and sends Cuotia a signed `payment.received` webhook. Cuotia owns the ledger: houses, dues, payments, aliases. It is **multi-tenant**: each conjunto sees only its own data. Pilot: Jardines de Ibiza (~45 houses, $30.000/month, one person holds the bank account).

## Commands

```bash
npm test                         # node:test, test/**/*.test.js
MASTER_KEY=$(openssl rand -hex 32) npm start
npm run admin -- crear-conjunto --slug ibiza --nombre "Jardines de Ibiza" --correo tesorera@ejemplo.com --llave @llave --titular "Titular"
npm run admin -- agregar-casa --conjunto ibiza --codigo 14 --residente "Sandra Duque"   # prints the resident's personal link
npm run admin -- generar-cuotas --conjunto ibiza --periodo 2026-11
```

No build step, no linter, **no runtime dependencies** (keep it that way: `node:sqlite`, `node:crypto`, `node:http`). Requires Node ≥ 22.5.

## Architecture

```
pagoradar ──signed webhook──▶ POST /webhooks/pagoradar/<tenantId> ─▶ verify with THAT tenant's secret ─▶ ingestEvent ─▶ store.forTenant(tenantId)
```

- **`src/app.js`**: plain `(req, res)` router. Per-conjunto webhook `/webhooks/pagoradar/<tenantId>` (HMAC check over the exact body *before* parsing, with the secret of the tenant in the URL), login/logout, panel, resident link `/r/<token>`, one static file.
- **`src/store.js`**: single SQLite DB, migrations `V1`… by `PRAGMA user_version` (never edit an earlier one). **Tenant isolation rule: all data of a conjunto is reached through `store.forTenant(id)`**, which closes over the tenant id. Never add a query on tenant data outside it. The only global lookups are `tenants`, `users`, `sessions` and `residentByToken` (the unguessable token is the credential). Every method that takes a house/payment id re-checks it belongs to the tenant. `test/isolation.test.js` guards this: extend it whenever you add a repo method.
- **`src/pagoradar.js`**: `ingestEvent` maps a verified event to ledger changes. **The conjunto is the one in the webhook URL** (whose secret signed the event); an optional `data.account.tenantRef` must equal it or the event is ignored (`tenant_mismatch`). It auto-settles only when the payer matches **one** house (remembered alias, else unique name match) **and** that house has an open due for exactly the amount; everything else goes to the "por asignar" queue. Never guess. Idempotent by pagoradar payment id, stored as `<tenantId>:<id>` so two conjuntos' pagoradars can reuse ids.
- **pagoradar config is per conjunto and lives in the DB, never in env.** `tenants.pagoradar_secret` is AES-GCM encrypted with `MASTER_KEY` (V3); the tenant DTO exposes only `pagoradarConfigured`/`pagoradarLastAt`, never the secret. Set from the panel (`/panel/ajustes`) or `npm run admin -- configurar-pagoradar`. No secret yet → the URL answers 503 so pagoradar retries. Any correctly signed event (even `payment.test`) updates `pagoradar_last_at`, which Ajustes shows as "Conectado". Do not reintroduce a global pagoradar secret.
- **Matching model:** dues are charged at the exact base amount (no unique-amount trick). `payments.assign(..., {rememberAlias})` teaches Cuotia the payer's name for next time.
- **`src/security.js`**: scrypt passwords, session/resident tokens (only SHA-256 hashes stored), pagoradar signature check (same algorithm as pagoradar's SDK: `Pagoradar-Signature: t=…,v1=HMAC(secret,"t.body")`, 5-minute tolerance), attempt limiter, AES-256-GCM `encryptSecret/decryptSecret` with `MASTER_KEY`, TOTP (RFC 6238, no library), per-session CSRF token.
- **Login is two steps and mandatory.** Password → a short session with `stage` `pending` (has TOTP) or `setup` (must enroll); only `/2fa` accepts it. A valid code → `sessions.promote` issues a *new* `full` session (token changes at privilege change). TOTP secrets are stored encrypted; `users.claimTotpStep` makes each code single-use. Lose `MASTER_KEY` and nobody can sign in: back it up. Every panel route requires `stage === "full"`.
- **First run: `/setup?token=…`.** With no conjunto in the DB, `server.js` prints a private one-use link (token = `SETUP_TOKEN` or random per boot). The form creates the first conjunto, its "Vigilancia" concept and the treasurer with a password they choose. `setupOpen` = no tenants AND `safeEqual(token)`; otherwise it answers the normal 404 so it never reveals whether setup exists. Re-checked synchronously after the async password hash so two simultaneous submits create one conjunto (tested). Wrong tokens are rate limited. There is deliberately **no open sign-up**: more conjuntos are created by the operator (CLI today).
- **`src/qr.js`: QR generator with no dependencies** (byte mode, level L, versions 1-9 = up to 230 bytes; `qrSvg` returns an inline SVG with colors as attributes because the CSP forbids inline styles). It draws the 2-step enrollment QR (an `otpauth://` link, ~100 bytes = version 5). It was verified against an independent decoder (jsQR, in a scratch dir, not a dependency) for every length 1-230 and against the page rendered in Chromium in light and dark mode. The repo's own tests (`test/qr.test.js`) read a symbol back (format info, mask, zigzag, Reed-Solomon, text) so a regression in placement or masking fails CI. Don't add a QR library; if the link ever exceeds 230 bytes, extend the tables to versions 10+ (16-bit character count).
- **Operations (`src/schedule.js`, `src/backup.js`, `scripts/admin.js`).** `generateAllDues` runs on boot and hourly from `server.js` (idempotent), so nobody has to press "Generar cuotas": without it a payment arriving before that finds no open due and waits in "por asignar". Adding or reactivating a house also generates the current period right away. `respaldar` uses `VACUUM INTO` (consistent while the app runs), never overwrites an existing file, names files to the second (`cuotia-AAAAMMDD-HHMMSS.db`, UTC) and prunes only files matching that name. `restablecer-2fa` / `restablecer-clave` are the recovery path for a lost authenticator or password (they also sign the user out everywhere). Changing the password from Ajustes needs the current one, is rate limited like login, and signs out every other session. HSTS is sent only when `PUBLIC_URL` is https. Bulk house import (`parseHouseLines` in `text.js`, `/panel/casas/importar`) shows each new personal link once, like a single new house.
- **Manual payments work without pagoradar** (`payments.recordManual`, `/panel/pagos/nuevo`). One payment can settle several dues of one house (they share `payment_id`), for exactly their sum: there are no partial payments. All or nothing inside a transaction; every due must be this house's, this tenant's and pending. `external_id` is `manual_<id>` (old cash ones are `cash_<id>`) and `payments.manual` is derived from that prefix, **not** from `method`, because pagoradar also reports `method: "transfer"`. The date is a Colombia-time day: today = now, a past day = noon that day (so it lands in the right month), future or before 2024 is refused. `revert` deletes a manual payment (it exists only here) and puts all its dues back to pending. `paymentMedium(p)` is the single label used by lists, receipts and the CSV. The resident pay screen says "avísale al tesorero" instead of "cuando el banco lo confirme" when the conjunto has no pagoradar secret.
- **Installable app (PWA).** `public/manifest.webmanifest` (treasurer, `start_url` `/panel`) and a **per-resident manifest** generated at `/r/<token>/manifest.webmanifest` (`start_url` and `scope` = that personal link, name "Cuotia · Casa 14"), so each resident installs an app that opens on their own due; `layout()` takes a `manifest` option and the three resident pages pass theirs. Icons are `public/icons/` (rounded `icon.svg`/PNGs for "any", full-bleed `maskable` and `apple-touch-icon` because the OS applies its own mask), generated from the two SVGs with Chromium (not a dependency); `favicon.ico` is a PNG-in-ICO of the 32 and 48 px. **`public/sw.js` must be served from `/` with `Cache-Control: no-cache`** (a cached worker can't be fixed) and **must never cache a page or a non-GET**: pages carry payments, names and personal tokens. It only network-first caches `/static/*` and answers navigations offline with `/offline`. `test/server.test.js` runs `sw.js` in a `node:vm` sandbox to prove those rules, and Chromium (`Page.getInstallabilityErrors`) reported no errors for both manifests. Not tested on a physical iPhone/Android. Bump `CACHE` in `sw.js` if the cached asset list changes.
- **How payments are confirmed** (V9 `tenants.pay_mode` `auto|manual|NULL`; Ajustes → "¿Cómo confirmas los pagos?"). The DTO exposes the effective `payMode` (NULL = `auto` if a pagoradar secret is saved, else `manual`). It only changes what the resident reads on the pay screen ("cuando el banco lo confirme" vs "cuando el tesorero registre tu pago" and a primary upload-proof button); the webhook works regardless of the mode.
- **Debts are monthly and tracked across months** (`src/debts.js`). `groupDebts(pending, houses, period)` turns `dues.listPending()` into one entry per owing house, ordered the way a treasurer chases: houses with **overdue** dues (a month before the current one) first, then the oldest debt, then the biggest, codes sorted numerically. The current month is "pendiente", only previous months are "atrasada"; at the turn of the month yesterday's pending becomes overdue by itself. `panel()` in `app.js` computes the groups once per request and passes `debts`/`owing` to every page: the sidebar badge on **Por cobrar**, `/panel/cobros` (filters `f=atrasadas|mes`, search `q`), the dashboard's arrears card and "Para cobrar primero", the status pill and button on **Casas**, and the payment form picker. The dashboard takes `?mes=YYYY-MM` (only months that have dues; anything else falls back to the current month, and generating dues is offered only for the current one). Row buttons open `/panel/pagos/nuevo?casa=<id>&cuota=<dueId>` (that due ticked; `todas=1` ticks all, none = the oldest); a successful manual payment redirects to `/panel/cobros?m=manual`. Per-house WhatsApp reminders use `personalReminder`; without a phone the link is `wa.me/?text=` so WhatsApp asks who to send it to (the personal resident link can't be included: only its hash is stored). **Any list of houses that owe must come from `groupDebts`, never recomputed in a view.** Links with several query parameters must write `&amp;` in literal template text (interpolated values are escaped, literals are not).
- **Payment window per conjunto** (V6, `tenants.open_day` / `due_day`, 1-28, NULL = not set; Ajustes → "Fechas de pago"). Informational for the resident ("Paga del 1 al 10 de noviembre", `paymentWindow`) and it drives lateness: `groupDebts(..., {dueDay, day})` marks a due `late` when its month is before the current one **or** it is this month's and today (Colombia) is after `dueDay`; that day itself is still on time. Views read `group.lateMonths` / `due.late`, never compare periods themselves. Payments are accepted and matched on any day: the dates never block anything.
- **Proofs of payment** (V7 `proofs`, `forTenant().proofs`, `src/upload.js`). A resident uploads a photo/PDF (≤ 5 MB) at `/r/<token>/comprobante` (multipart parsed by hand; the type comes from the **magic bytes**, never from the browser, SVG/HTML are refused; max 3 pending per house; rate limited; same-origin). Bytes live in SQLite (backups include them) and only come back through `proofs.file(id)` for the treasurer, at `/panel/comprobantes/<id>/archivo` with `nosniff`, `default-src 'none'; sandbox`, `no-store` and a PDF forced to download. They appear in "Comprobantes por revisar" on the Resumen (and in the sidebar badge); **Registrar pago** with `comprobante=<id>` passes `proofId` to `recordManual`, which marks it `accepted` inside the same transaction; `revert` puts it back to `pending`; rejecting keeps the file. The upload page deliberately has no auto-refresh (it would clear the chosen file).
- **Team** (V8 `invitations`, `forTenant().team`, global `invitations.byToken/accept`). Ajustes → Equipo: any signed-in member invites by email; the link `/invitacion/<token>` (7 days, one use, only its hash stored, shown once) lets that person choose a name and password in the **inviting** conjunto, then they sign in and enroll their own 2-step code like anyone. Everyone has the same power (role stays `tesorero`); you can't remove yourself or the last person; removing deletes their sessions. Emails are globally unique, so an email of another conjunto can't be invited. Rate limited like setup.
- **Search is instant and works without JavaScript.** Lists carry `data-search`, inputs `data-live-filter` (and the empty-message id in `data-live-empty`); `public/app.js` filters as you type and hides the search button, Enter opens the only match's `[data-pick]` link. A `<select>` with many options gets a hidden `data-select-filter` input that the script reveals and that rebuilds the options. **`fold`/`matches` in `public/app.js` and `foldText`/`matchesSearch` in `src/text.js` must stay identical** (accent-less, case-less, every word in any order): the no-JS server search and the browser must answer the same; a test runs both on the same table. Use the `[hidden]` attribute (global `display:none !important`), not inline styles.
- **Months that were never generated.** Dues exist only for generated months (boot and hourly generate the current one). `dues.generateForHouse(house, period)` and `/panel/casas/<id>/mes` (the `+ Octubre` buttons in the payment form) add one month to one active house and return to the form with it ticked; `POST /panel/cuotas/generar` with `mes=` adds a month for every active house. `validPastPeriod` in `app.js`: a real month, not the future, at most 24 back. Both are idempotent (`INSERT OR IGNORE`), so the only way to double-charge is not available.
- **Every panel POST** checks same Origin **and** the session's `_csrf` form field (`csrfToken(sessionToken)`, HMAC of the HttpOnly cookie value). Flash messages come from a fixed list keyed by `?m=`; never reflect query text. **`Referrer-Policy` must stay `same-origin`**: with `no-referrer` browsers post forms with `Origin: null` and the Origin check refuses every login (found by a real-browser run; `fetch` tests can't see it).
- **`src/views.js` + `src/http.js`**: server-rendered HTML. The `html` tagged template escapes every interpolation unless it is `html`/`raw()` output; use it for all markup. CSP is `default-src 'self'` with no inline styles or scripts: use classes in `public/app.css`, never `style=""`.
- **Design:** the approved mockup canvas is https://claude.ai/artifact/57BSgLaPW6LwbXJpm8bk8L; the layout must keep matching it. Tokens and layout in `public/app.css`: palette **"Menta clara"** (chosen by the owner over four other options) = deep green ink `#0b4a3a` (buttons, sidebar, tab bar, receipt page), mint accent `#c9efdc`, a **light mint hero card** (`--hero-bg`, text `--hero-fg`; the hero's buttons are ink, never the old lime-on-dark), ground `#f3f8f6`. Mobile first, always light: there is deliberately NO automatic dark mode, a user whose OS is dark must still see the approved design. App icons, favicon, manifests and `theme-color` use the same green/mint (icons regenerated from the SVGs with Chromium; `favicon.ico` is rebuilt from the 32 and 48 px PNGs). The earlier mockup canvas (ink + lime, dark hero) is **outdated** in colors only. **Shell** (`panelLayout` in `views.js`): dark sidebar from 900px, bottom tab bar below it; every treasurer page goes through it and gets `{tenant,user,csrf,badge,houseCount,cuota}` from `base` in `app.js`. **Resident pages** have no shell: home (`/r/<token>`), how to pay (`/r/<token>/pagar`, refreshes itself every 20 s and redirects home once nothing is pending) and receipt (`/r/<token>/recibo/<dueId>`, only for a paid due of that house; "Descargar PDF" is the browser's print with a print stylesheet). **Font:** Plus Jakarta Sans variable, self-hosted in `public/fonts/` (SIL OFL, licence file alongside); only the files listed in `STATIC` in `app.js` are served. **Script:** `public/app.js` only adds copy/print buttons (`data-copy`, `data-print`); the CSP allows scripts from this origin only, so no inline scripts and no `style=""`.
  Mockup features not built (needs a decision first): a payable QR on the pay screen (a Bre-B QR is bank-specific; pagoradar holds the account's QR image), a due date ("Vence el 10"), a public transparency card, the resident's bottom bar ("Comunidad").

## Conventions

- User-facing strings (UI, errors, logs, docs) are **Spanish (Colombian)**; code identifiers and comments are English.
- Money is integer cents (`amountCents`); show with `peso()`. Periods are `"YYYY-MM"` in Colombia time (`currentPeriod()`).
- Tests: `node:test` + in-memory store, **made-up data only**. `test/fixtures.js` has `twoConjuntos()` and `paymentEvent()`.
- Deployment: Docker Compose on Dokploy. Data volume pinned to `cuotia-data`; don't rename it.

## Houses, history and undo

- A house is never deleted: `houses.setActive(false)` keeps all history but closes its personal link, skips it in `dues.generate` and in matching (`aliases.houseFor` and `matchHouse` only see active houses), and its **unpaid** dues stop counting in `summary`/`listByPeriod` (its **paid** ones keep counting).
- `payments.list({period,status,houseId,q,limit,offset})` is the history (newest first). `period` is a Colombia-time month (`periodRange`, UTC-5). The search escapes `LIKE` wildcards and skips the payer-name clause when the needle normalizes to nothing. The CSV (`/panel/pagos.csv`) is `;`-separated with a UTF-8 BOM (what Spanish Excel opens correctly) and every cell goes through `csvCell`, which neutralizes a leading `= + - @` so a payer's name can't run as a spreadsheet formula. Tests read the BOM from raw bytes because `fetch().text()` strips it.
- `payments.revert` undoes an assignment: the due returns to pending; a bank payment goes back to "por asignar" and the alias learned for that house is deleted; a cash payment (which exists only here) is deleted. The UI hides it inside `<details>` so a stray tap does nothing and no script is needed.
- Any new route that takes a house, alias or payment id must go through `forTenant` methods that re-check ownership, and needs a case in the "un tesorero no puede ver ni tocar…" server test.

## Not built yet (next steps)

- Passkeys; self-service recovery (today the operator runs `restablecer-2fa` / `restablecer-clave`); off-server copy of the backups (they land on the same disk).
- Operator panel to create conjuntos (CLI only today), WhatsApp reminders, public transparency page, expenses, administración as a second concept.
- Cuotia doesn't create pagoradar charges: residents pay the exact amount to the conjunto's Bre-B key and the payer's name does the matching. A payer reverted from a house can still auto-match it again through a unique match with the resident's name.
